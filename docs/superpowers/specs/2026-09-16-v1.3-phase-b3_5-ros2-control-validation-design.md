## 1. Executive Summary & Objective

Phase B3 established the software command safety layer (`GuardedRobotBackend`, `CommandSafetySupervisor`, `CommandWatchdog`, and `ROS2ControlReadinessProbe`) and validated middleware transport. However, **end-to-end closed-loop validation against real `ros2_control` controller plugins (`ForwardCommandController`, `JointStateBroadcaster`, and hardware interface plugins) has not yet been executed.**

The primary objective of **Phase B3.5** is to close this validation debt by executing full closed-loop testing against real ROS2 Humble `ros2_control` controllers using official example hardware (`ros2_control_demo_example_3` RRBot).

## 2. Critical Safety & Scope Mandates

1. **NO PHYSICAL HARDWARE COMMANDING:**  
   Phase B3.5 executes exclusively against fake/example simulation hardware (`ros2_control_demo_example_3`). Zero physical robot drivers, zero vendor robot APIs, zero IP configuration, zero motor drive enables.
2. **NO HARDWARE E-STOP / STO CLAIMS:**  
   All halts remain non-safety-rated application-level software stops via `request_software_stop()`.
3. **NO CONTROLLER SWITCHING FROM VISIONROBOTTWIN APPLICATION:**  
   VisionRobotTwin runtime must create **ZERO** clients for mutating services (`SwitchController`, `LoadController`, `UnloadController`, `ConfigureController`, `SetHardwareComponentState`, `ReloadControllerLibraries`). Tests launch separate isolated processes for position mode and velocity mode with controllers already active.
4. **PERMANENT B1 & B2 INVARIANCE:**  
   `ROS2JointStateBackend` remains permanently read-only. `ROS2SimulationBackend` remains designated for simulation environments only.
5. **REAL STATE FEEDBACK REQUIREMENT:**  
   Acceptance of position and velocity command paths strictly requires **observed state change** on `/joint_states` via `ROS2JointStateBackend`, not merely message publication.

## 3. Test Target: Official `ros2_control_demo_example_3` (RRBot)

The official ROS2 Humble package `ros2_control_demo_example_3` provides an RRBot (2-DoF revolute robot) configured with multiple command and state interfaces:
- **Available Controllers:**
  - `forward_position_controller` (`position_controllers/JointGroupPositionController`) claiming `joint1/position`, `joint2/position`.
  - `forward_velocity_controller` (`velocity_controllers/JointGroupVelocityController`) claiming `joint1/velocity`, `joint2/velocity`.
  - `joint_state_broadcaster` (`joint_state_broadcaster/JointStateBroadcaster`) exporting state interfaces (`position`, `velocity`).
- **Hardware Plugin:**
  - `ros2_control_demo_example_3/RRBotSystemMultiInterfaceHardware` (C++ dynamic plugin integrating with controller manager control loops).

## 4. Headless Launch & Subprocess Lifecycle Management

To avoid graphical dependencies (such as RViz or GUI plugins) and ensure deterministic execution on CI runners:
1. **Headless Launch Strategy:**
   - Execute the official launch file with `gui:=false` or `rviz:=false` if exposed, or construct a test-specific launch script invoking the official RRBot robot description URDF and `ros2_control` controller manager configuration YAML.
2. **Process Lifecycle Management (`ROS2ControlTestHarness`):**
   - Launches controller manager and example nodes in a dedicated background subprocess.
   - Uses bounded polling (with monotonic timeouts) to verify:
     - `controller_manager` ROS node discovery.
     - `ListControllers` service availability.
     - Expected controller transitions to `active`.
     - Initial `/joint_states` reception.
   - Guarantees complete process termination (`SIGTERM` followed by `SIGKILL` if necessary) in a `finally` block to prevent orphaned processes or topic cross-talk between test cases.

## 5. End-to-End Validation Specifications

### 5.1 Position Controller Closed-Loop Acceptance Flow
1. **Launch Environment:** Start RRBot with `forward_position_controller` and `joint_state_broadcaster` active.
2. **Preflight Introspection:**
   - Query `ROS2ControlReadinessProbe` (inspects `ListControllers`, `ListHardwareComponents`, `ListHardwareInterfaces`).
   - Verify expected controller is `active`, type matches `JointGroupPositionController`, and command interfaces `joint1/position`, `joint2/position` are claimed.
3. **Negative Probe Tests:**
   - Probe with mismatched controller name or missing interface -> verify probe reports `ready_to_arm = False` and `guarded_backend.arm()` is blocked.
4. **Backend Setup & Arming:**
   - Initialize `ROS2SimulationBackend(command_mode="position")` and wrap with `GuardedRobotBackend`.
   - Enable simulation commands (`enable_simulation_commands()`) and arm guard (`arm()`).
5. **Command & Closed-Loop Feedback:**
   - Record initial measured positions $q_{0}$.
   - Send bounded target positions $q_{\text{target}} = [0.25, -0.25]$ (within RRBot limit bounds).
   - Poll `guarded_backend.get_joint_state()` until observed joint positions move toward $q_{\text{target}}$ within tolerance.
6. **Shutdown:**
   - `disarm()`, `disconnect()`, terminate demo subprocess.

### 5.2 Velocity Controller Closed-Loop & Watchdog Flow
1. **Launch Environment:** Start RRBot in a fresh process with `forward_velocity_controller` and `joint_state_broadcaster` active.
2. **Preflight Introspection:**
   - Verify `forward_velocity_controller` is `active` and claims `joint1/velocity`, `joint2/velocity`.
3. **Backend Setup & Arming:**
   - Initialize `ROS2SimulationBackend(command_mode="velocity")` wrapped in `GuardedRobotBackend` with `command_watchdog_timeout_s=0.2`.
   - Enable simulation commands and arm guard.
4. **Command & Motion Feedback:**
   - Record initial position $q_{0}$.
   - Send positive velocity command $v_{\text{target}} = [0.2, 0.2]$.
   - Observe $q(t)$ advancing in the commanded direction over time.
5. **Software Stop Validation:**
   - Invoke `request_software_stop()`.
   - Verify zero-velocity command is dispatched to `/forward_velocity_controller/commands`.
   - Verify joint positions stop advancing within practical test tolerance.
6. **Watchdog Timeout Validation:**
   - Re-arm, send velocity command $v_{\text{target}}$, and stop sending subsequent commands.
   - Allow $> 0.2\text{s}$ to elapse.
   - Trigger `check_watchdog()` -> verify `COMMAND_WATCHDOG_TIMEOUT` fault is latched and zero-velocity halt is published.
7. **Shutdown:**
   - `disconnect()`, terminate demo subprocess.

## 6. Joint Ordering & QoS Policy Rules

1. **Joint Ordering Validation:**
   - Float64MultiArray command payloads are dimensionless vectors without explicit joint name headers.
   - Test harness explicitly asserts that the joint order declared in `ROS2SimulationBackendConfig.state_config.expected_joint_names` strictly matches the joint order configured in the controller YAML (`joint1`, `joint2`).
2. **Command QoS Policy:**
   - System Default QoS is tested against real Humble forward controllers. If communication succeeds without message loss, System Default QoS is locked as the validated standard.

## 7. B4 Readiness Gate Decision Rule

The **Phase B4 Readiness Gate** will transition from **BLOCKED** to **SATISFIED** if and only if **ALL** of the following conditions are met:
1. Exact-head Windows CI (Python 3.11 & 3.12) is 100% green.
2. Exact-head ROS2 Humble CI is 100% green with real `ros2_control` packages installed.
3. Real forward position controller end-to-end validation passes with verified state feedback.
4. Real forward velocity controller end-to-end validation passes with verified state feedback.
5. Privileged software stop and watchdog halt are confirmed via real velocity controller telemetry.
6. Zero mutating `controller_manager` service calls are made from VisionRobotTwin.
7. Zero physical hardware commands dispatched.
8. v1.2 reference benchmarks and baseline suites remain untouched and green.

If any required controller-level validation is omitted or skipped, the **B4 Readiness Gate remains BLOCKED.**
