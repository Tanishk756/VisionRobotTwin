## 1. Executive Summary & Objective

In **VisionRobotTwin v1.2** and **v1.3 Phase A1**, execution transport was successfully isolated into `RobotBackend` (`PyBulletRobotBackend` / `MockRobotBackend`). However, robot kinematic modeling remained coupled to direct PyBullet simulation calls:
- `p.calculateInverseKinematics` in `GenericIKSolver`
- `p.calculateJacobian` in `robotics/kinematics.py` and `ResolvedRateController`
- `p.getLinkState` in `GenericRobotController.get_end_effector_pose()` and `compute_fk_at_configuration`
- Temporary joint resets (`p.resetJointState`) for off-state candidate forward kinematics queries

The objective of **Phase A2** is to establish the **KinematicsProvider Boundary**, decoupling forward kinematics (FK), spatial geometric Jacobians, and raw inverse kinematics (IK) from simulation engines.

```
+───────────────────────────────────────────────────────────────────────────────────────────────────+
|                                    1. EXECUTION / TRANSPORT LAYER                                 |
|                                         (RobotBackend)                                            |
| Owns: Connection lifecycle, joint state acquisition, command transport, motion stop.              |
+───────────────────────────────────────────────────────────────────────────────────────────────────+
                                                  │
                                                  ▼
+───────────────────────────────────────────────────────────────────────────────────────────────────+
|                                  2. KINEMATICS & MODEL COMPUTATION                                |
|                                       (KinematicsProvider)                                        |
| Owns: State-preserving FK, spatial Jacobian (J_lin, J_ang, J_full), and raw numerical IK solves.  |
| Does NOT own: Execution buses, application IK validation policy, or pure linear algebra.         |
+───────────────────────────────────────────────────────────────────────────────────────────────────+
                                                  │
                                                  ▼
+───────────────────────────────────────────────────────────────────────────────────────────────────+
|                                     3. WORLD & COLLISION MODEL                                    |
|                                        (CollisionProvider)                                        |
| Owns: Collision scene representation, obstacle queries, self-collision distance (Phase A3).       |
+───────────────────────────────────────────────────────────────────────────────────────────────────+
```

## 2. Separation of Responsibilities & Boundaries

To prevent over-abstraction and maintain clear architectural boundaries:

### 2.1 What `KinematicsProvider` Owns
1. **Forward Kinematics (`compute_fk`)**: Computes end-effector Cartesian position $[x,y,z]$ and unit quaternion $[x,y,z,w]$ for any candidate joint configuration $\mathbf{q} \in \mathbb{R}^n$.
2. **State-Preserving Safety**: Guarantees that evaluating candidate $\mathbf{q}$ does not alter the active physics simulation state (joint angles, velocities, forces, or stepping clock).
3. **Spatial Geometric Jacobian (`compute_jacobian`)**: Computes $(\mathbf{J}_{\text{lin}}, \mathbf{J}_{\text{ang}}, \mathbf{J}_{\text{full}})$ of shape $(3,n)$, $(3,n)$, $(6,n)$ for a candidate $\mathbf{q}$.
4. **Raw Numerical Inverse Kinematics (`solve_ik_raw`)**: Computes candidate arm joint angles $\mathbf{q}_{\text{raw}} \in \mathbb{R}^n$ for target position $\mathbf{p}$ and optional orientation $\mathbf{q}_{\text{target}}$ using the underlying model engine.

### 2.2 What `KinematicsProvider` Does NOT Own (Pure Mathematics & Application Policies)
- **Pure Mathematical Algorithms**:
  - `ManipulabilityMetrics` calculation (`compute_manipulability` via SVD)
  - Adaptive Damped Least-Squares pseudoinverse (`compute_damped_pseudoinverse`)
  - Orientation error quaternion algebra
  - Null-space projection and joint-centering gradients
  - Trajectory generation (Quintic polynomial / SLERP interpolation)
- **Application IK Validation Policy (`GenericIKSolver`)**:
  - Cartesian target finite/NaN checks
  - Spherical reachability distance boundary rejection
  - Joint limit tolerance checks and boundary clamping
  - FK residual verification ($e_{\text{pos}} \le \text{max\_residual\_position\_m}$, $e_{\text{orn}} \le \text{max\_residual\_orientation\_rad}$)
  - `IKStatus` / `IKResult` diagnostic reporting
- **Transport & Command Dispatch (`RobotBackend` / `GenericRobotController`)**:
  - Joint velocity rate limiting and slew clamping
  - Motor command transmission

## 3. Contract Specifications

### 3.1 `KinematicsProvider` Abstract Base Class

```python
from abc import ABC, abstractmethod
from typing import Optional, Sequence, Tuple
import numpy as np


class KinematicsProvider(ABC):
    """Abstract interface for robot kinematic modeling and spatial computations."""

    @abstractmethod
    def compute_fk(
        self, joint_positions: Sequence[float]
    ) -> Tuple[np.ndarray, np.ndarray]:
        """Calculates end-effector (position [x,y,z], quaternion [x,y,z,w]) for candidate joint configuration q.

        Must be strictly state-preserving.

        Args:
            joint_positions: Joint angles for controllable arm joints (rad).

        Returns:
            Tuple of (position np.ndarray shape (3,), quaternion_xyzw np.ndarray shape (4,)).
        """
        pass

    @abstractmethod
    def compute_jacobian(
        self, joint_positions: Sequence[float]
    ) -> Tuple[np.ndarray, np.ndarray, np.ndarray]:
        """Calculates spatial geometric Jacobian for candidate joint configuration q.

        Args:
            joint_positions: Joint angles for controllable arm joints (rad).

        Returns:
            Tuple of (J_linear (3,n), J_angular (3,n), J_full (6,n)).
        """
        pass

    @abstractmethod
    def solve_ik_raw(
        self,
        target_position: Sequence[float],
        target_orientation: Optional[Sequence[float]] = None,
        lower_limits: Optional[Sequence[float]] = None,
        upper_limits: Optional[Sequence[float]] = None,
        joint_ranges: Optional[Sequence[float]] = None,
        rest_poses: Optional[Sequence[float]] = None,
        joint_damping: Optional[Sequence[float]] = None,
        max_iterations: int = 100,
        residual_threshold: float = 1e-4,
    ) -> Tuple[float, ...]:
        """Invokes model engine numerical IK solver to calculate candidate joint angles.

        Args:
            target_position: Desired [x, y, z] target in base frame.
            target_orientation: Optional unit quaternion [x, y, z, w].
            lower_limits: Optional per-joint lower limits.
            upper_limits: Optional per-joint upper limits.
            joint_ranges: Optional per-joint ranges.
            rest_poses: Optional per-joint rest poses.
            joint_damping: Optional per-joint damping factors.
            max_iterations: Maximum solver iterations.
            residual_threshold: Convergence threshold.

        Returns:
            Tuple of candidate joint positions (rad) matching controllable arm joints.
        """
        pass
```

## 4. Evaluation of IK Architecture: Validation vs Solver Separation

### Architectural Trade-off Evaluation
1. **Approach A (Monolithic Provider)**: Move full `GenericIKSolver` validation and `IKResult` generation into `PyBulletKinematicsProvider`.
   - *Drawback*: Couplings to `IKStatus`, reachability policies, and error tolerance configuration would leak into every kinematics provider implementation. Future analytical or pinocchio providers would duplicate validation code.
2. **Approach B (Layered Separation: Recommended)**:
   - `KinematicsProvider.solve_ik_raw(...)`: Pure model solve producing candidate $\mathbf{q}_{\text{raw}}$.
   - `KinematicsProvider.compute_fk(...)`: State-preserving forward kinematics for residual checking.
   - `GenericIKSolver`: Pure, backend-independent validation orchestrator managing reachability pre-checks, joint limit checks, FK residual evaluation, and `IKResult` construction.
   - *Advantage*: High cohesion, zero duplication, clean dependency inversion, completely decoupled from PyBullet.
3. **Approach C (Separate `IKSolverProvider` ABC)**:
   - *Drawback*: Excessive abstraction (violates YAGNI). In robot kinematics, numerical IK is an intrinsic model capability of the engine.

### Final Ruling on IK Architecture
Adopt **Approach B**. `GenericIKSolver` delegates raw numerical computation to `self.provider.solve_ik_raw()` and residual evaluation to `self.provider.compute_fk()`.

## 5. `PyBulletKinematicsProvider` Design & Safety

### 5.1 Constructor & State
```python
class PyBulletKinematicsProvider(KinematicsProvider):
    def __init__(
        self,
        physics_client_id: int,
        robot_body_id: int,
        arm_joint_indices: Sequence[int],
        end_effector_link_index: int,
        default_ee_orientation: Tuple[float, float, float, float] = (1.0, 0.0, 0.0, 0.0),
    ) -> None:
        ...
```

### 5.2 State-Preserving FK Semantics & Concurrency Safety
- PyBullet `getLinkState` evaluates FK on the currently loaded joint configuration.
- To compute FK at candidate $\mathbf{q}$ without disturbing running physics:
  1. Acquire internal `threading.RLock()`.
  2. Query and save current joint positions and velocities using `p.getJointStates`.
  3. Apply candidate $\mathbf{q}$ via `p.resetJointState(..., targetVelocity=0.0)`.
  4. Query `p.getLinkState(..., computeForwardKinematics=True)`.
  5. In a `finally` block, unconditionally restore original positions and velocities.
  6. Release `threading.RLock()`.
- **Zero Physics Steps**: `p.stepSimulation()` is **never** called during FK queries.

### 5.3 Jacobian Column Slicing & Movable Joint Padding
- PyBullet `p.calculateJacobian` computes partial derivatives with respect to **all movable joints** (revolute + prismatic, including gripper fingers).
- To preserve mathematical parity with v1.2:
  1. Discover all movable joint indices $M$.
  2. Pad candidate $\mathbf{q}$ with zeros to length $|M|$.
  3. Call `p.calculateJacobian`.
  4. Slice the first $n$ columns corresponding to controllable arm joints:
     $$\mathbf{J}_{\text{lin}} = \mathbf{J}_{\text{trans}}[:, :n], \quad \mathbf{J}_{\text{ang}} = \mathbf{J}_{\text{rot}}[:, :n], \quad \mathbf{J}_{\text{full}} = \begin{bmatrix} \mathbf{J}_{\text{lin}} \\ \mathbf{J}_{\text{ang}} \end{bmatrix} \in \mathbb{R}^{6 \times n}$$

## 6. End-Effector Pose Ownership Decision

In Phase A1, `GenericRobotController.get_end_effector_pose()` remained direct PyBullet code as documented transitional technical debt.

### Decision
`GenericRobotController` will hold a reference to `KinematicsProvider` (defaulting to `PyBulletKinematicsProvider` instantiated at setup).
- `GenericRobotController.get_end_effector_pose()` delegates directly:
  ```python
  def get_end_effector_pose(self) -> Tuple[np.ndarray, np.ndarray]:
      return self.kinematics_provider.compute_fk(self.get_current_joint_positions())
  ```
- This eliminates all runtime direct `p.getLinkState` calls from `GenericRobotController`.
