## 1. Safety & Operational Ground Rules

> [!CAUTION]
> **MANDATORY NON-SAFETY-RATED SOFTWARE DISCLAIMER**  
> `VisionRobotTwin` software guards, watchdog timers, position/velocity limits, and software halt mechanisms are **defensive software layers only and are strictly NON-SAFETY-RATED**.  
> They **DO NOT** replace, satisfy, or bypass:
> - Certified hardware Emergency Stop (E-Stop) circuitry compliant with ISO 13849-1 / IEC 62061 (PLd/PLe or SIL 2/3).
> - Hardware Safe Torque Off (STO) and Safe Operating Stop (SOS) systems.
> - Hardware protective-stop interlocks, light curtains, area scanners, and physical cell fencing.
> - Hardware safety PLCs and safety-rated robot controller functions.
> - Required trained operator presence, clearance procedures, and dedicated manual E-Stop pendants.

### Operating Rules
1. **Zero Motion in Design & B4.1 Framework Phases**: Zero commands shall be dispatched to physical hardware.
2. **Zero Inferred Hardware**: Physical simulation support in PyBullet (e.g. Franka Panda or KUKA iiwa URDFs) **does not imply** physical hardware connectivity. Target hardware remains `UNRESOLVED` until explicit hardware selection and documentation review.
3. **Decoupled Software vs Physical Gates**:
   - **`B4.1 SOFTWARE FRAMEWORK COMPLETE`**: Declared when the vendor-neutral data schemas, protocols, read-only state backend, limit provenance engine, mock adapters, and soak framework pass 100% CI.
   - **`B4.1 PHYSICAL COMMISSIONING COMPLETE`**: Remains **`BLOCKED — TARGET UNRESOLVED`** until physical hardware is selected and physically commissioned on-premise. Mock tests do NOT close the physical commissioning gate.
   - **`PHASE B4.2 (PHYSICAL COMMANDING)`**: Remains strictly **`BLOCKED`**.
4. **No Controller Manager Mutation**: `VisionRobotTwin` shall not invoke mutating services (`SwitchController`, `LoadController`, `UnloadController`, `ConfigureController`, `SetHardwareComponentState`) on real hardware controller managers.
5. **No Automatic Drive Enable or Fault Clearing**: `VisionRobotTwin` shall not clear vendor hardware faults, reset protective stops, bypass E-Stops, or automatically power drives. All physical energization remains an external operator procedure.

### 3.1 Three-State Safety Logic & Normalized Signals: `SafetySignalState`
To prevent semantic ambiguity (e.g. `emergency_stop_active = SAFE`), all safety fields are named as positive normalized conditions evaluated against `SafetySignalState`:

```python
class SafetySignalState(Enum):
    """Three-state evaluation for safety-critical hardware signals."""
    SAFE = "SAFE"        # Condition is positively verified, healthy, and acceptable.
    UNSAFE = "UNSAFE"    # Condition indicates an active fault, hazard, or stop condition.
    UNKNOWN = "UNKNOWN"  # Condition is not exposed, disconnected, stale, or unparsed.
```

**Rule**: `UNKNOWN` is strictly treated as `UNSAFE` for command authorization. Physical motion requires all mandatory signals to be explicitly `SAFE`.

## 4. Verification Policies & Invariants

### 4.1 Identity Matching Policy
Physical command authorization requires an exact match between actual `PhysicalRobotIdentity` and the configured `ExpectedPhysicalRobotIdentity`:
- `vendor` must match exactly (case-sensitive).
- `model` must match exactly (case-sensitive).
- `joint_count` must match model DoF exactly.
- `joint_names` and order must match canonical model joint ordering exactly.
- `serial_number` must match when configured.
- Any discrepancy raises `HardwareIdentityMismatchError` and fails closed (`eligible_for_future_command_commissioning = False`).

### 4.2 Model Matching Policy
Incoming physical joint state telemetry is mapped against `ResolvedRobotModel`:
- No silent joint reordering.
- Missing expected joint -> `JointStateMappingError`.
- Non-finite joint position -> `JointStateMappingError`.
- Extraneous joints -> filtered strictly if declared, or rejected if inconsistent.

### 4.3 Limit Provenance & Interval Intersection Policy
For each joint, gather available position intervals and velocity limits across valid sources (`LimitSource`):
- **Effective Position Lower Bound**: $\max(\text{all lower bounds})$
- **Effective Position Upper Bound**: $\min(\text{all upper bounds})$
- **Intersection Consistency Check**: If $\text{effective\_lower} > \text{effective\_upper}$, the provenance is **inconsistent and INVALID**. Future command commissioning is blocked.
- **Effective Max Velocity**: $\min(\text{all positive finite velocity limits})$ across valid trusted sources.

### 4.4 Freshness Policy
Physical telemetry freshness is evaluated against `physical_state_timeout_s`:
- State age $t_{\text{now}} - t_{\text{receive}} > \text{physical\_state\_timeout\_s}$ marks state as stale.

### 4.5 Zero-Command Audit in B4.1
Phase B4.1 guarantees absolute observation isolation:
- `PhysicalRobotStateBackend` declares `RobotBackendCapabilities(read_only=True, position_commands=False, velocity_commands=False, effort_limit_override=False, halt_motion=False)`.
- Invoking `command_joint_positions`, `command_joint_velocities`, or `halt_motion` raises `ReadOnlyBackendError`.
- Zero position command messages, zero velocity command messages, zero trajectory action goals, zero service requests to controller managers.

## 5. B4.1 Motionless Observation Soak Test

A deterministic, passive observation test designed to run against connected hardware or mock physical adapter:
1. **Setup**: Connect `PhysicalRobotStateBackend` to telemetry provider with physical drives stationary.
2. **Telemetry Ingestion (`PhysicalObservationSession`)**:
   - Collect received joint state packets over configured duration/samples.
   - Compute sample count, maximum receive gap $\Delta t_{\max}$, mean interval, stale-state incidents, identity-change incidents, model-mismatch incidents, and safety-state transitions.
   - Assert zero outgoing command packets and zero mutating service calls.
3. **Acceptance Criteria**:
   - $\Delta t_{\max} \le \text{physical\_state\_timeout\_s}$.
   - Stable identity, zero dropped required channels, zero command side-effects.

### 6.1 Triple Authorization Layer
Physical motion requires all three layers to be concurrently satisfied:
- **Layer 1 (Hardware/Vendor Layer)**: Robot controller in remote/external control mode, drives enabled, hardware safety chain closed and reported `SAFE`.
- **Layer 2 (Software Authorization Layer)**: `PhysicalCommissioningProfile` loaded, readiness checks passed, operator confirmation recorded, `enable_physical_commands()` called.
- **Layer 3 (Guard Layer)**: `GuardedRobotBackend.arm()` successful (`SafetyGuardState.ARMED`), zero active faults.

### 6.2 Commissioning Profile & Envelopes

```python
class PhysicalCommissioningMode(Enum):
    """Restricted commissioning modes for initial physical validation."""
    OBSERVE_ONLY = "OBSERVE_ONLY"
    LOW_SPEED_POSITION = "LOW_SPEED_POSITION"
    LOW_SPEED_VELOCITY = "LOW_SPEED_VELOCITY"

@dataclass(frozen=True)
class PhysicalCommissioningProfile:
    """Immutable constraints bounding physical robot commissioning."""
    profile_id: str
    expected_identity: PhysicalRobotIdentity
    mode: PhysicalCommissioningMode
    max_velocity_fraction: float        # e.g., 0.10 (strictly <= 0.10 for initial commissioning)
    max_position_step_rad: Tuple[float, ...]
    allowed_joint_subset: Optional[Tuple[str, ...]]
    workspace_bounding_box: Optional[Tuple[Tuple[float, float], Tuple[float, float], Tuple[float, float]]]
    physical_state_timeout_s: float
    command_watchdog_timeout_s: float
    required_safety_signals: Tuple[str, ...]
    operator_session_id: str
```

### 6.3 Command Transports & Trajectory Strategy
- **Position Mode**: Prefer `joint_trajectory_controller` (`FollowJointTrajectory` action) or validated forward position streaming with hardware interpolation.
- **Velocity Mode**: Bounded forward velocity commands with multi-layer watchdog.
- **Command Acknowledgement**: Physical backend tracks driver transmission, controller receipt, and observed physical joint motion independently from local dispatch.

### 6.4 Halt & Fault Recovery
- `halt_motion()` executes a non-safety-rated software stop (zero-velocity / trajectory cancel).
- Any hardware fault or timeout transitions `GuardedRobotBackend` to `FAULT_LATCHED`.
- Recovery requires explicit operator fault clearance on the physical robot, followed by `reset_fault()` and `arm()`. Automatic retry is strictly prohibited.

## 7. Traceability, Credentials & CLI Architecture

### 7.1 Commissioning Session Traceability: `CommissioningSessionRecord`
Every physical session records an immutable `CommissioningSessionRecord`:
- Git Commit SHA (`software_commit_sha`), working tree status (`working_tree_clean`), timestamp, session ID.
- Verified `PhysicalRobotIdentity` and driver versions.
- Tested profile, configured limits, observed outcomes, and fault logs.
- Excludes passwords, network keys, or proprietary tokens.

### 7.2 CLI Separation Policy
- `main.py` shall **not** include physical hardware execution flags during B4.
- Standalone commissioning CLI (`tools/physical_commissioning.py`) is **deferred** until an explicit target is selected and approved.
