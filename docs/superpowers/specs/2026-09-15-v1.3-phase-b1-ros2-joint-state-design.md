**Status**: APPROVED DESIGN (Design & Planning Phase)  
**Target Platform**: Ubuntu 22.04 LTS / ROS2 Humble Hawksbill  
**Baseline Compatibility**: Windows 11 / Python 3.11 & 3.12 (Zero ROS Dependency on Windows)

## 1. Executive Summary & Architectural Motivation

With the completion of **Phase A4**, `GenericRobotController` has been fully decoupled from PyBullet:
- Model metadata is governed by `ResolvedRobotModel` (canonical roles, limits, velocities, forces).
- Execution transport is abstracted by `RobotBackend`.
- Kinematics calculations are abstracted by `KinematicsProvider`.
- Spatial collision queries are abstracted by `CollisionProvider`.

**Phase B1** establishes the first real-world transport layer: **Read-Only ROS2 Joint State Telemetry Consumption**.

```
+-------------------------------------------------------------------------+
|                              ROS 2 Graph                                |
|  [robot_state_publisher / joint_state_broadcaster / hardware driver]    |
|                                    |                                    |
|                      sensor_msgs/msg/JointState                         |
|                       Topic: e.g. /joint_states                         |
+------------------------------------+------------------------------------+
                                     |
                                     v
+-------------------------------------------------------------------------+
|                  VisionRobotTwin Execution Layer                        |
|                                                                         |
|  +-------------------------------------------------------------------+  |
|  |                    ROS2JointStateBackend                          |  |
|  |  - Private rclpy.Context & SingleThreadedExecutor background thread|  |
|  |  - Name-based joint re-ordering & extra-joint pruning             |  |
|  |  - Pure read-only safety guard (Commands fail closed)             |  |
|  |  - Clock domain isolation (source timestamp vs receive timestamp)  |  |
|  +---------------------------------+---------------------------------+  |
|                                    |                                    |
|                                    v                                    |
|                        TimestampedJointState                            |
|                                    |                                    |
|             +----------------------+----------------------+             |
|             |                                             |             |
|             v                                             v             |
|  GenericRobotController (Read-Only)          Diagnostic Probe Tool      |
|  - get_current_joint_positions()             (tools/ros2_probe.py)      |
|  - get_current_joint_velocities()            - Rate & Latency stats     |
|  - get_end_effector_pose() (via FK)          - Health status            |
+-------------------------------------------------------------------------+
```

### Key Architectural Invariants
1. **Strictly Read-Only**: Absolutely NO command publishing, action client, or controller manager interaction in Phase B1.
2. **Deterministic Joint Mapping**: Messages are matched by string joint name against `expected_joint_names` (from `ResolvedRobotModel.arm_joint_names`), never by raw array indices.
3. **Clock Domain Separation**: Source timestamps (ROS header) are isolated from local receipt timestamps (monotonic clock) to ensure reliable freshness calculation.
4. **Zero Impact on Windows / PyBullet**: All ROS2 modules are strictly optional. Standalone Windows environments without `rclpy` continue running all 214 tests with zero regressions.

## 2. Process & Lifecycle Architecture

### 2.1 Architecture Evaluation
| Approach | Description | Pros | Cons | Recommendation |
| :--- | :--- | :--- | :--- | :--- |
| **A. Embedded rclpy Backend** | Backend manages a private `rclpy.Context` and `SingleThreadedExecutor` on a dedicated background thread. | Low latency, direct `RobotBackend` compliance, self-contained. | Must strictly isolate ROS context to avoid process-wide side effects. | **RECOMMENDED FOR B1** |
| **B. Separate ROS Bridge Process** | Auxiliary process receives ROS2 messages and transmits to main app via IPC (shared memory / sockets). | Total process isolation; crashes cannot bring down vision loop. | Over-engineered for read-only joint telemetry; introduces IPC serialization overhead. | Deferred (re-evaluate for physical command phases). |
| **C. External Node Injection** | Application externally passes a pre-existing ROS2 node into the backend. | Clean for ROS-native wrappers. | Breaks standalone execution for VisionRobotTwin core scripts. | Rejected for core backend. |

### 2.2 Lifecycle & Threading Contract
`ROS2JointStateBackend` implements standard `connect()` / `disconnect()` lifecycle using private ROS context:
- **`connect()`**:
  1. Initializes private `rclpy.context.Context()`.
  2. Creates node `node_name` inside `node_namespace` with configured `domain_id`.
  3. Creates subscription to `joint_state_topic` using configured QoS profile.
  4. Spawns a dedicated background daemon thread running `rclpy.spin(node, executor=executor)`.
  5. Returns `True` immediately without blocking or waiting for the first message.
- **`disconnect()`**:
  1. Signals executor to stop.
  2. Joins executor background thread with a bounded timeout (e.g. 2.0s).
  3. Destroys subscription and node.
  4. Shuts down **only** the backend's private `rclpy.Context`.
  5. Sets internal health status to `DISCONNECTED`.
- **Private vs Global Context Invariant**:
  `ROS2JointStateBackend` must NEVER call global `rclpy.shutdown()`. It operates strictly on `self._context.shutdown()`, preventing interference with any external ROS nodes operating within the same process.

## 3. Telemetry Ingestion & Mapping Contract

### 3.1 Message Source Contract
- **Message Type**: `sensor_msgs/msg/JointState`
- **Topic**: Configurable (Default `/joint_states`)
- **Expected Message Fields**:
  - `header.stamp`: `builtin_interfaces/msg/Time` (sec, nanosec)
  - `name`: `string[]`
  - `position`: `float64[]`
  - `velocity`: `float64[]` (Optional/may be empty in some drivers)
  - `effort`: `float64[]` (Optional/may be empty)

### 3.2 Canonical Joint Name Mapping & Ordering
ROS2 drivers frequently publish joint states in arbitrary order or include extraneous joints (gripper fingers, chassis joints, virtual joints).

1. **Mapping Invariant**:
   Given configured `expected_joint_names = (name_1, name_2, ..., name_N)`:
   - Construct name index map: `lookup = {name: idx for idx, name in enumerate(msg.name)}`.
   - Verify every required name exists: `all(req_name in lookup for req_name in expected_joint_names)`.
   - Extract in exact configured order:
     - `positions = tuple(msg.position[lookup[name]] for name in expected_joint_names)`
     - `velocities = tuple(msg.velocity[lookup[name]] for name in expected_joint_names)` (if velocity array provided)
     - `efforts = tuple(msg.effort[lookup[name]] for name in expected_joint_names)` (if effort array provided)
2. **Pruning Extraneous Joints**:
   Any joint present in `msg.name` that is not in `expected_joint_names` is safely ignored.
3. **Deterministic Rejection Rules (Malformed Telemetry)**:
   A message is marked invalid and dropped if:
   - `msg.name` is empty.
   - `msg.name` contains duplicate entries (ambiguous mapping).
   - Any joint in `expected_joint_names` is missing.
   - `len(msg.position) != len(msg.name)` (when positions present).
   - `len(msg.velocity) != 0 and len(msg.velocity) != len(msg.name)`.
   - `len(msg.effort) != 0 and len(msg.effort) != len(msg.name)`.
   - Any mapped position, velocity, or effort contains `NaN` or `+/-Inf`.
4. **Resilient Failure Handling**:
   Malformed messages increment `invalid_messages_count` in telemetry diagnostics, log a debug warning, and do **NOT** raise an unhandled exception or replace the last valid cached state.

## 4. Clock Domains, Freshness, & Health Semantics

### 4.1 Clock Domain Separation
```
+-----------------------------------+-----------------------------------+
|       Source Clock Domain         |        Local Clock Domain         |
| (ROS Header / Middleware / Sim)   |       (time.monotonic())          |
+-----------------------------------+-----------------------------------+
|  msg.header.stamp (sec, nanosec)  |  receive_timestamp_s             |
|  Preserved for trace diagnostics  |  Used for freshness & timeouts    |
+-----------------------------------+-----------------------------------+
```
- **Rule**: Never evaluate staleness by subtracting `time.monotonic()` from `source_timestamp_s`.
- `receive_timestamp_s` is captured via `time.monotonic()` at the moment the callback acquires the message.
- `age_s(current_time_s)` is calculated as `max(0.0, current_time_s - self.receive_timestamp_s)`.

### 4.2 State Availability & Health State Transitions
`BackendHealthStatus` adheres to the following state machine:

```
[ Unconnected ] ---> connect() ---> [ CONNECTED_WAITING_FOR_STATE (DEGRADED) ]
                                                |
                                    First valid message arrives
                                                v
                                      [ HEALTHY ] <-----------+
                                        |      ^               |
     time.monotonic() - last_receive > timeout |   Fresh valid message
                                        v      |               |
                                      [ DEGRADED ] ------------+
```

1. **`DISCONNECTED`**: Prior to `connect()` or after `disconnect()`.
2. **`DEGRADED`**:
   - Connected, but zero valid messages received yet.
   - Connected, but time since last valid message exceeds `state_timeout_s` (default `0.5s`).
3. **`HEALTHY`**: Connected, and `age_s <= state_timeout_s`.
4. **`ERROR`**: Unrecoverable background thread or ROS middleware failure.

### 4.3 `get_joint_state()` Semantics
- **Before First Message**: Raises `BackendStateUnavailableError` ("No joint state received yet on topic /joint_states").
- **Stale State (`age > timeout`)**: Returns the last known valid `TimestampedJointState`. Callers/diagnostics inspect `health_status() == DEGRADED` or `state.age_s()` to take application-level precautions.

## 5. Read-Only Safety & Command Fail-Closed Policy

`ROS2JointStateBackend` implements `RobotBackend`. Because Phase B1 is read-only, all command methods **MUST FAIL CLOSED**:

```python
class ReadOnlyBackendError(RuntimeError):
    """Raised when a command operation is attempted on a read-only execution backend."""
    pass
```

- **`command_joint_positions(target_positions)`**: Raises `ReadOnlyBackendError("ROS2JointStateBackend is strictly read-only and does not support position commanding.")`
- **`command_joint_velocities(target_velocities, effort_limit)`**: Raises `ReadOnlyBackendError("ROS2JointStateBackend is strictly read-only and does not support velocity commanding.")`
- **`halt_motion()`**: Raises `ReadOnlyBackendError("ROS2JointStateBackend is strictly read-only; halt_motion() cannot halt physical hardware.")`
  - *Invariant*: `halt_motion()` must NOT silently succeed or log "motion stopped" when no command was transmitted.

class ROS2JointStateBackendConfig:
    """Configuration for ROS2 read-only joint state subscriber backend."""

## 7. Optional Dependency Isolation & Multi-Platform Strategy

### 7.1 Import Isolation
- `robotics/backends/ros2_joint_state_backend.py` encapsulates all `rclpy` and `sensor_msgs` imports.
- `robotics/backends/__init__.py` exposes `ROS2JointStateBackend` lazily or safely without top-level import failure.
- If instantiated in an environment where `rclpy` is absent, `ROS2JointStateBackend.__init__` raises:
  ```python
  class OptionalDependencyError(ImportError):
      pass
  ```
  with an explicit error message: `"ROS2 dependencies (rclpy, sensor_msgs) are required to use ROS2JointStateBackend. Install ROS2 Humble and source the environment."`

### 7.2 Separation of Pure Parser & ROS Middleware
To guarantee complete unit test coverage on Windows without installing ROS2:
- `robotics/backends/ros2_state_mapping.py` defines pure parsing and validation functions (`parse_joint_state_dict`, `extract_ros_timestamp`) that operate on Python dictionaries / duck-typed message structures.
- Full parity tests for all rejection and reordering rules run natively in Windows CI.

## 8. Acceptance Criteria & Phase B2 Boundary

### Phase B1 Acceptance Criteria
1. **Zero Regression**: All 214 existing Phase A4 tests pass on Windows Python 3.11 & 3.12.
2. **Pure Mapping Tests**: Comprehensive unit tests covering all valid, permuted, extra, missing, and malformed joint state payloads.
3. **Isolated Context**: Private `rclpy.Context` created and destroyed without touching global process state.
4. **Safety Verification**: 100% fail-closed rejection on `command_joint_positions`, `command_joint_velocities`, and `halt_motion`.
5. **Real ROS2 Integration**: Automated tests in Linux ROS2 Humble environment publishing real `sensor_msgs/msg/JointState` messages and validating canonical reception.
6. **Diagnostic CLI Probe**: `tools/ros2_joint_state_probe.py` streams live joint angles and health without commanding robot.

### Excluded from Phase B1 (Phase B2+ Boundary)
- **NO command transport**: No `JointTrajectory` publisher, no `FollowJointTrajectory` action client.
- **NO controller manager interaction**: No switching or querying `ros2_control` hardware interfaces.
- **NO TF2 listener**: No base-to-camera or base-to-flange frame lookups via ROS TF.
- **NO `/robot_description` or URDF XML parsing over ROS**: `ResolvedRobotModel` remains canonical.
- **NO modification to `main.py` CLI default**: PyBullet simulator remains default.
