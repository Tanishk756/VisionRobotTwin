# Phase B4 Implementation Plan: Controlled Physical Robot Integration Architecture

**Document Version**: 1.1.0  
**Target Milestone**: VisionRobotTwin v1.3.0  
**Target Branch**: `develop/v1.3.0`  
**Physical Adapter Target**: `UNRESOLVED` (Vendor-Neutral Infrastructure)  
**Execution Strategy**: Sequential Gate Division (B4.1 Read-Only Framework -> B4.2 Low-Speed Command)

---

## 1. Overview & Phased Roadmap

Phase B4 establishes the foundational architecture for integrating physical robotic manipulators into `VisionRobotTwin`. To maintain strict safety discipline, Phase B4 is divided into decoupled milestones:

1. **Phase B4.1 — Vendor-Neutral Physical Read-Only Commissioning Framework**:
   - Implements vendor-neutral physical identity, normalized three-state safety abstractions, and strictly read-only physical state backend.
   - Implements limit provenance engine with interval intersection.
   - Implements mock physical telemetry adapter for unit/contract tests.
   - Validates motionless observation, zero-command audit, and model-matching telemetry against `ResolvedRobotModel`.
   - Executes motionless soak tests with zero physical command side-effects.
   - **Gate Outcome**: `PHASE B4.1 SOFTWARE FRAMEWORK COMPLETE`, while `PHASE B4.1 PHYSICAL COMMISSIONING` remains `BLOCKED — TARGET UNRESOLVED`.
2. **Phase B4.2 — Guarded Low-Speed Physical Commanding (Deferred & Blocked)**:
   - Implements vendor-specific low-speed command transports under triple-authorization gating.
   - Validates hardware software-stop and watchdog timeout behavior.
   - Requires formal physical target hardware selection and physical commissioning approval before implementation.

## 2. Phase B4.1 Detailed Task Breakdown

### Task 1: Physical Identity & Three-State Safety Schemas
- **Objective**: Implement immutable dataclasses and enums for physical identity, safety status, and signal evaluation.
- **Files**:
  - `robotics/backends/physical_identity.py`
  - `tests/test_physical_identity.py`
- **Key Deliverables**:
  - `SafetySignalState` (`SAFE`, `UNSAFE`, `UNKNOWN`).
  - `PhysicalRobotIdentity` (vendor, model, serial, identifier, firmware, revision, joint names, timestamps).
  - `PhysicalSafetyStatus` (normalized fields: `communication_healthy`, `vendor_fault_clear`, `protective_stop_clear`, `emergency_stop_clear`, `external_control_ready`, `drives_state_safe_or_known`, `operational_mode_safe`, `brakes_state_safe_or_known`, timestamps).
  - `ExpectedPhysicalRobotIdentity` and `HardwareIdentityMismatchError`.

### Task 2: Physical Readiness Provider & Report Framework
- **Objective**: Implement `PhysicalTelemetryProvider` protocol, `PhysicalReadinessProvider` protocol, and `PhysicalReadinessReport` structure.
- **Files**:
  - `robotics/backends/physical_readiness.py`
  - `tests/test_physical_readiness.py`
- **Key Deliverables**:
  - `PhysicalTelemetryProvider` protocol (pure read-only methods: `connect`, `disconnect`, `is_connected`, `read_joint_state`, `read_identity`, `read_safety_status`, `health_status`).
  - Evaluates identity match, model DoF/order match, state freshness, fault status, and safety chain completeness.
  - Generates actionable diagnostics with fail-closed semantics (`ready_for_observation` vs `eligible_for_future_command_commissioning`).

### Task 3: Target-Neutral Mock Physical Hardware Adapter
- **Objective**: Build a simulated/mock physical adapter implementing `PhysicalTelemetryProvider` for unit and contract testing.
- **Files**:
  - `tests/mocks/mock_physical_adapter.py`
  - `tests/test_mock_physical_adapter.py`
- **Key Deliverables**:
  - Emulates healthy, faulted, stale, and mismatched physical robot hardware states.
  - Asserts 0 command methods and 0 side-effects.

### Task 4: Physical Read-Only State Backend (`PhysicalRobotStateBackend`)
- **Objective**: Implement a strictly read-only execution backend wrapping `PhysicalTelemetryProvider` and `ResolvedRobotModel`.
- **Files**:
  - `robotics/backends/physical_state_backend.py`
  - `tests/test_physical_state_backend.py`
- **Key Deliverables**:
  - Ingests joint positions, velocities, efforts, and hardware timestamps.
  - Enforces `ReadOnlyBackendError` on `command_joint_positions`, `command_joint_velocities`, and `halt_motion`.
  - Implements `transport_capabilities` (`read_only=True`, commands/halt=False).
  - Implements `diagnostics()` and health reporting.

### Task 5: Model & Limit Provenance Validation Engine
- **Objective**: Implement `LimitSource` and interval intersection limit validation.
- **Files**:
  - `robotics/backends/physical_validation.py`
  - `tests/test_physical_validation.py`
- **Key Deliverables**:
  - Position lower bound = $\max(\text{lower bounds})$; upper bound = $\min(\text{upper bounds})$.
  - Inconsistent bounds ($\text{lower} > \text{upper}$) mark provenance as `INVALID`.
  - Max velocity = $\min(\text{positive finite velocity limits})$.

### Task 6: Motionless Observation Soak & Zero-Command Audit Suite
- **Objective**: Implement automated soak testing and command isolation audits.
- **Files**:
  - `tests/test_physical_observation_soak.py`
- **Key Deliverables**:
  - `PhysicalObservationSession` collecting sample counts, max receive gaps, stale incidents, identity/model changes, and safety transitions.
  - Proves zero position/velocity commands dispatched during observation.

### Task 7: Commissioning Traceability Logging
- **Objective**: Create immutable commissioning session record logging.
- **Files**:
  - `robotics/backends/commissioning_session.py`
  - `tests/test_commissioning_session.py`
- **Key Deliverables**:
  - Immutable `CommissioningSessionRecord` schema with `software_commit_sha`, `working_tree_clean`, session ID, timestamps, target identity, provider info, resolved model ID, readiness summary, and fault summary. Zero secrets stored.

### Task 8: Pytest Markers & B4.1 Milestone Review
- **Objective**: Register `physical_hardware` and `manual_commissioning` markers in `pytest.ini`. Validate 100% CI pass and close B4.1 software framework gate.
