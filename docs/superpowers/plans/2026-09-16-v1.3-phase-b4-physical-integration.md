# Phase B4 Implementation Plan: Controlled Physical Robot Integration Architecture

**Document Version**: 1.0.0  
**Target Milestone**: VisionRobotTwin v1.3.0  
**Target Branch**: `develop/v1.3.0`  
**Physical Adapter Target**: `UNRESOLVED` (Vendor-Neutral Infrastructure)  
**Execution Strategy**: Sequential Gate Division (B4.1 Read-Only -> B4.2 Low-Speed Command)

---

## 1. Overview & Phased Roadmap

Phase B4 establishes the foundational architecture for integrating physical robotic manipulators into `VisionRobotTwin`. To maintain strict safety discipline, Phase B4 is divided into two decoupled milestones:

1. **Phase B4.1 — Physical Read-Only Commissioning**:
   - Implements vendor-neutral physical identity, three-state safety abstractions, and read-only physical state backends.
   - Validates motionless observation, zero-command audit, and model-matching telemetry against `ResolvedRobotModel`.
   - Executes motionless soak tests with zero physical command side-effects.
2. **Phase B4.2 — Guarded Low-Speed Physical Commanding (Deferred)**:
   - Implements vendor-specific low-speed command transports under triple-authorization gating.
   - Validates hardware software-stop and watchdog timeout behavior.
   - Requires formal B4.1 acceptance and target hardware selection before implementation.

## 2. Phase B4.1 Detailed Task Breakdown

### Task 1: Physical Identity & Three-State Safety Schemas
- **Objective**: Implement immutable dataclasses and enums for physical identity, safety status, and signal evaluation.
- **Files**:
  - `robotics/backends/physical_identity.py` (New module)
  - `tests/test_physical_identity.py` (New test suite)
- **Key Deliverables**:
  - `SafetySignalState` (`SAFE`, `UNSAFE`, `UNKNOWN`).
  - `PhysicalRobotIdentity` (vendor, model, serial, joint names, timestamps).
  - `PhysicalSafetyStatus` (communication, faults, protective stop, E-stop, drives).

### Task 2: Physical Readiness Provider & Report Framework
- **Objective**: Implement `PhysicalReadinessProvider` protocol and `PhysicalReadinessReport` structure.
- **Files**:
  - `robotics/backends/physical_readiness.py` (New module)
  - `tests/test_physical_readiness.py` (New test suite)
- **Key Deliverables**:
  - Evaluates identity match, model DoF/order match, state freshness, fault status, and safety chain completeness.
  - Generates actionable diagnostics with fail-closed semantics (`ready_for_observation` vs `ready_for_command`).

### Task 3: Target-Neutral Mock Physical Hardware Adapter
- **Objective**: Build a simulated/mock physical adapter implementing physical identity, state telemetry, and safety signals for unit and contract testing.
- **Files**:
  - `tests/mocks/mock_physical_adapter.py`
  - `tests/test_mock_physical_adapter.py`
- **Key Deliverables**:
  - Emulates healthy, faulted, stale, and mismatched physical robot hardware states.
  - Demonstrates strict isolation from real hardware during standard CI.

### Task 4: Physical Read-Only State Backend (`PhysicalRobotStateBackend`)
- **Objective**: Implement a strictly read-only execution backend wrapping physical telemetry sources.
- **Files**:
  - `robotics/backends/physical_state_backend.py`
  - `tests/test_physical_state_backend.py`
- **Key Deliverables**:
  - Ingests joint positions, velocities, efforts, and hardware timestamps.
  - Enforces `ReadOnlyBackendError` on all command methods.
  - Implements `diagnostics()` and health reporting.

### Task 5: Model & Telemetry Validation Engine
- **Objective**: Integrate physical state validation with `ResolvedRobotModel` and `CommandSafetyConfig`.
- **Files**:
  - `robotics/backends/physical_validation.py`
  - `tests/test_physical_validation.py`
- **Key Deliverables**:
  - Enforces limit provenance resolution (most restrictive limit wins).
  - Verifies joint name order, DoF parity, and non-finite number rejection.

### Task 6: Motionless Observation Soak & Zero-Command Audit Suite
- **Objective**: Implement automated soak testing and command isolation audits.
- **Files**:
  - `tests/test_physical_observation_soak.py`
  - `tests/test_physical_zero_command_audit.py`
- **Key Deliverables**:
  - Proves zero position/velocity commands dispatched during observation.
  - Verifies zero mutating controller-manager service calls.
  - Measures state frequency, packet drop rate, and jitter over configured durations.

### Task 7: Commissioning Checklists & Traceability Logging
- **Objective**: Create physical commissioning procedures, preflight checklists, and session record logging.
- **Files**:
  - `robotics/backends/commissioning_session.py`
  - `docs/checklists/physical_commissioning_checklist.md`
  - `tests/test_commissioning_session.py`
- **Key Deliverables**:
  - Immutable `CommissioningSessionRecord` schema.
  - Step-by-step preflight, observation-only, and safety verification guides.

### Task 8: B4.1 Review & Milestone Acceptance Gate
- **Objective**: Validate complete Phase B4.1 test pyramid, verify documentation integrity, and close B4.1 gate.

## 4. Acceptance Criteria & Gate Rules

### 4.1 Phase B4.1 Acceptance Criteria
To declare Phase B4.1 complete, the following criteria must be satisfied:
1. All Phase B4.1 unit, mock, and contract test suites pass 100% on Windows and Linux CI.
2. `PhysicalRobotIdentity` and `PhysicalSafetyStatus` correctly enforce three-state fail-closed semantics.
3. Zero commands are dispatched during connection, state observation, or health queries.
4. Model matching correctly blocks mismatched DoF, joint names, or ordering.
5. Motionless observation soak test completes with zero state dropouts exceeding timeout thresholds.
6. Zero mutating controller-manager service calls are made.
7. Application version remains `VisionRobotTwin 1.3.0-dev`.

### 4.2 Phase B4.2 Entry Gate
Phase B4.2 commissioning motion remains strictly **BLOCKED** until:
1. Phase B4.1 is fully accepted and validated.
2. Physical hardware target, vendor driver, and network topology are explicitly selected and documented.
3. Manufacturer safety manuals and external hardware safety chains (E-Stop, STO, cell interlocks) are verified operational by a trained operator.
4. Low-speed commissioning profile and limit provenance are reviewed and approved.
5. Dedicated commissioning tool `tools/physical_commissioning.py` is invoked with interactive operator authorization.
